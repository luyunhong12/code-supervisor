# ub-mode 24 项督导清单（中文工作表）

本工作表参考 Robert C. Martin 的 ub-mode，由本项目整理为中文并补充检查方法。原作采用 [MIT 许可证](../licenses/ub-mode-MIT.txt)。它是普通 Markdown，不注册 Skill。
每次审查为每项记录：适用范围、证据、结论（通过/问题/待判断/未执行/不适用）、下一步。
下面的“工具支持”不是自动证明整条原则已经满足。

| 序号 | 原则 | 要检查什么 | 工具支持与人工判断 |
|---|---|---|---|
| 1 | 减少重复决策 | 同一规则只保留一个事实来源，改动规模满足实际需求 | dryer/jscpd 找候选；人工判断是否同一业务规则 |
| 2 | 基础先行 | 数据结构正确，先做后续共同依赖的工作；避免不必要的共享状态 | 类型检查辅助，数据模型/并发边界人工审查 |
| 3 | 测试驱动 | 行为修复先看到预期失败，再最小修复；不写失真的测试凑数 | pytest/CTest 验证，AI记录失败到通过的证据 |
| 4 | 从需求重新审视设计 | 新需求是否暴露旧设计不合适，能否分步改到合理结构 | 人工审查需求与模块职责 |
| 5 | 质疑共同前提 | 同一前提下两次修复仍失败，写明前提并检查不平衡由哪些参与者持有，先纠正错误分配 | 复现实验与领域分析，不能自动套模式 |
| 6 | 先减后加 | 能否删掉无效状态、路径或抽象，再新增逻辑 | 静态检查/变异给线索，删除需行为证据 |
| 7 | 以可验证结果为目标 | 验收标准明确；中间破坏仅在可控、可恢复计划内发生 | acceptance 与回归测试，用户确认需求边界 |
| 8 | 建造辅助工具 | 重复或难观察的工作先手工验证一个单位，再自动化 | 本项目适配器及反例测试；不自动化未经验证的错误流程 |
| 9 | 领域建模 | 用结构排除非法状态，保持术语一致，清楚且局部的实现不强行抽象 | 类型检查辅助；维护项目领域术语表 |
| 10 | 边界纪律 | 外部数据在入口校验，内部使用已验证值，纯计算与副作用分开 | 安全/类型/测试辅助；审查输入契约 |
| 11 | 类型纪律 | 非法值难以表达，解析只做一次，不压制编译器反馈 | Pyright、真实编译、clang-tidy |
| 12 | 幂等操作 | 重复执行或崩溃恢复后达到一致状态 | 项目补充重复执行/故障恢复验收 |
| 13 | 共享状态先隔离 | 不需要共享则独立，需要共享则明确单一写入者 | TSan 检查触发的竞争；所有权人工审查 |
| 14 | 修根因 | 先复现，不以吞异常/加保护掩盖根因 | 回归用例与原始失败证据 |
| 15 | 可验证的小步骤 | 完成一个修改并验证，再开始下一个 | 分项报告、Git提交；不把多个无关修复捆绑 |
| 16 | 测行为而非实现 | 从使用者接口验证可观察结果，不能只断言存在/未抛错 | 变异测试、性质测试及独立预期值 |
| 17 | Crapper | 目标函数 CRAP<10，增加有效测试或合理拆分；复杂分支允许有依据的例外 | Python 原版 crapper；C++ 当前分别报告复杂度/覆盖率 |
| 18 | Dryer | 检查相似度>=0.8的候选，确认相同语义后消除重复 | 原版 dryer；C++ 使用 jscpd，其指标不等价 |
| 19 | Mutator | 补未覆盖、处理存活、删除确认无用代码 | Python 原版算子及 C++ 有限算子；先排除等价变异和执行错误 |
| 20 | 重构 | 固定原行为、改变结构、证明行为保持 | 回归、覆盖及变异证据，不能仅看格式差异 |
| 21 | 工作日志 | 记录重要动作和原因，完成时汇报 | 分项日志/哈希/报告；AI另记设计决策 |
| 22 | 控制上下文 | 保留关键约束和摘要，大量证据放文件 | 本地证据目录；不能因上下文短省略检查 |
| 23 | 工作区清理 | 确认不再使用后清理，未提交工作先保留 | 不自动删除目标工程/工作树；只清理已确认临时产物 |
| 24 | 提交与推送 | 小步提交，说明原因、变化和验证 | 遵守用户当前授权与仓库分支规则；本Markdown不自动授权推送主分支 |

规范叠加：Python 使用项目约定的 Google 风格中文说明与 Black；C++ 使用 Doxygen 中文说明。
Doxygen只处理文档，C++命名、格式、所有权等另按项目代码规范审查。
项目规则参见 [代码规范](coding-standard.md) 和 [结构规则](architecture.md)。
