
# 0-0、代码规范（通用）

## 1. 适用范围与使用方式

本规范可复制到不同项目，适用于应用程序、服务、工具和设备软件，不绑定具体框架、协议或目录名称。
通用结构规则见 [结构与拆分规则](architecture.md)。

在新项目的 `docs/` 中保存这两份通用文档，再建立 `0、代码规范.md` 和
`1、代码结构与拆分规则.md`，记录项目使用的语言、格式工具、数据约定、模块和验证命令。
通用文档提供默认要求；项目文件可以明确覆盖某项要求，但须写明理由和适用范围。
不要直接照搬其他项目的 IP、路径、业务名称、文件数量和构建命令。

README 提供规范入口；使用开发代理时，可在项目已有的 AGENTS.md 中引用规范。
仅复制文档不会自动约束其他项目，需要将其纳入该项目的开发约定或评审流程。
不强制改写第三方源码和生成代码；在维护自有代码时遵守本规范。

## 2. 基本原则

* 正确性优先，接口含义明确，失败行为可判断，资源和状态归属清楚。
* 代码、注释、文档和测试保持一致，不用错误注释解释真实行为。
* 采用当前语言和项目的习惯写法，不跨语言强推同一命名或排版风格。
* 复杂度来自实际需求；不为了可能出现的功能预先创建空类、空接口和多层转发。
* 不机械逐行注释；注释解释用途、边界、原因和维护时容易误解的地方。

## 3. 中文注释的三个层次

| 层次       | 要说明的内容                                                 |
| ---------- | ------------------------------------------------------------ |
| 文件或模块 | 负责什么、属于哪个功能边界                                   |
| 类型和函数 | 用途、输入输出、返回值、失败方式、生命周期和副作用           |
| 关键流程   | 校验顺序、边界处理、提交时机、资源释放、异常和并发处理的理由 |

自有代码使用中文说明，保留必要的英文标识和协议术语。
类和结构体说明职责；具有业务含义的成员说明单位、范围、初始值、索引或所有权。
接口声明和实现分离时，两处都应有足以独立理解的说明；不能只在实现处写“详见声明”。
接口含义变化时同步更新两处。短函数的说明可以简短，但不能遗漏关键限制。
匿名函数若只是简单转发，可在所在调用处解释；承担独立业务逻辑时应命名提取或完整说明。

## 4. 函数契约应说明什么

1. 完成的任务，而非只重复函数名。
2. 每个参数的含义、方向，以及适用的单位、范围、空值和索引规则。
3. 返回值的含义，包括空结果、失败和部分成功。
4. 预期异常或错误返回的触发条件。
5. 对外部系统、输入参数、对象状态或资源的修改。
6. 阻塞、超时、线程安全、调用顺序和引用有效期等实际存在的约束。

输出参数失败时是保持、清空还是部分更新，要明确写出。
不声称实现没有提供的原子性、线程安全、性能或实时保证。
只写适用内容，不为 void 函数虚构返回值，不逐项罗列所有标准库分配异常。

## 5. 不同语言的注释形式

### 5.1 C / C++

文件使用 Doxygen `@file/@brief`，类型和函数使用 `/** ... */`。
**头文件声明和 `.c/.cpp` 函数定义均需中文说明**，包括构造、析构和私有辅助方法。
实现处不能只添加文件头；关键流程使用 `//` 说明。成员可使用 `///<`。
头文件中的简单访问器和删除的特殊成员可以使用简短的 `///`。

```cpp
/**
 * @brief 从输入路径加载并校验配置，成功后替换输出对象。
 * @param[in] path 配置文件路径，不能为空。
 * @param[out] result 成功时更新；失败时保持调用前的值。
 * @param[out] error 成功时清空；失败时填写可定位的原因。
 * @return 完整加载成功返回 true，否则返回 false。
 * @note 本示例采用错误返回方式，具体项目必须与实际实现一致。
 */
bool load_config(const std::string & path, Config & result, std::string & error);
```

实现前同样写清接口含义，函数内再解释“先校验临时结果，全部成功后提交”等设计。

### 5.2 Java

使用中文 Javadoc 描述类型、构造函数和方法，按实际情况写 `@param`、`@return`、`@throws`。
接口和实现类的方法都要有可理解的说明，不能仅依赖继承注释隐藏实现特有的限制。
不使用 C++ 的参数方向标记作为强制语法，在参数文字中说明可变对象是否被修改。

### 5.3 Python：Google 风格文档字符串

Python 统一采用 **Google 风格文档字符串＋中文说明**，基本排版遵循
[PEP 257](https://peps.python.org/pep-0257/)，分区形式参考
[Google Python Style Guide](https://google.github.io/styleguide/pyguide.html#383-functions-and-methods)。

使用三双引号，写在模块、类或函数体开头。先用一句话概括职责；需要补充时，
空一行说明约束、副作用或使用条件，再按实际需要填写以下分区：

1. `Args:`：参数含义；注明必要的单位、范围、坐标系、数组形状和时间语义。
2. `Returns:` 或 `Yields:`：结果含义；元组逐项说明，字典说明关键字段。
3. `Raises:`：调用方需要处理的异常及其触发条件。
4. 类的公开属性使用 `Attributes:`；构造参数可以在 `__init__` 的 `Args:` 中说明。

分区名称保留英文，内容使用中文，代码标识符不翻译。分区正文缩进四空格；
同一条说明换行后再缩进四空格。摘要、详细说明和各分区之间空一行，
多行文档字符串的结束引号独占一行。不要使用 `@param`、`@return` 等 Doxygen 标签。

**按复杂度选择长度，不为形式填充栏目：**

- 简单函数、测试用例和含义明确的内部辅助函数可以只有一句清楚的说明。
- 公共接口、复杂计算、配置处理、文件写入和进程控制接口，应分开说明实际契约。
- 没有有效返回值时不写 `Returns: None`，没有相关异常时不凑 `Raises:`。
- 类型注解已明确表达的类型不重复罗列；单位、形状、语义和约束仍须说明。
- 不列举所有可能的运行时异常，不把已捕获并转成结果的错误写成会向外抛出。
- 副作用、非原子操作、线程归属及超时后可能已执行的动作，写在详细说明中。
- 不用分号把用途、参数、返回值和异常挤进同一句，不以注释数量判断质量。

例如，具有文件副作用的接口可以写成：

```python
def write_json(path, value):
    """将数据写入 JSON 文件，并原子替换目标文件。

    使用 UTF-8 编码。先在目标目录写入临时文件，完整写入后
    再替换目标文件，避免读到写入一半的报告。

    Args:
        path: 目标文件路径；父目录不存在时自动创建。
        value: 可序列化为 JSON 的数据，不允许包含 NaN 或无穷大。

    Raises:
        TypeError: 数据包含无法序列化的对象。
        ValueError: 数据包含非有限浮点数或循环引用。
        OSError: 目录创建、文件写入或替换失败。
    """
```

上述异常必须与实际实现一致，不能原样复制到行为不同的函数。
函数内部使用 `#` 解释算法依据、关键限制和选择原因，不逐行翻译代码。
格式工具负责排版，不负责验证注释是否真实或契约是否完整。

### 5.4 其他语言及配置

其他语言使用其支持的文档注释工具，不机械套用 Doxygen 或 Python 分区。
配置和构建脚本解释单位、默认值、适用条件和非显然的安排，不逐行翻译语法。

## 6. 命名、格式与数据表达

项目规范必须选定语言对应的命名和自动格式工具；已有一致约定优先沿用。
一般避免含糊缩写，名称反映业务含义，不用变量名承担所有解释工作。
格式以工具配置为准，禁止混用缩进、尾随空格和无理由的大范围格式改动。
复杂条件和多个操作不要压成一行，简单守卫语句可按项目风格保留短写法。

数字须明确单位、范围和有无符号；通信和文件数据须明确编码、字节顺序和索引起点。
可配置的数据和展示文案与稳定业务标识分开，不使用显示名称隐式决定程序分支。
避免到处散落相同常量；也不要将一次使用且含义清楚的值都包装成抽象对象。

## 7. 状态、资源与错误处理

* 明确每份可变状态由谁更新；连接、文件、线程等资源必须有清晰的释放路径。
* 失败后留下什么状态、是否允许重试、是否已经产生副作用，应在接口中说明。
* 不吞掉异常或错误，也不在多层重复记录同一错误。日志应有定位信息，避免泄露凭据。
* 需要多个步骤共同完成时，明确部分成功如何处理，不能假装所有步骤是原子操作。
* 区分当前数据、缓存数据和无效数据；时间和超时使用与需求匹配的时钟。
* 并发访问需要明确同步方案；不要把“目前单线程使用”描述成“类本身线程安全”。

## 8. 配置、效率与验证

配置进入业务流程前完成类型、范围、缺项和冲突校验。需要热更新时定义加载、校验、
切换和失败回退规则；不要求所有项目都只能启动时加载。

减少实际重复的网络请求、磁盘访问和解析；是否缓存、批量处理或并发，应以语义和测量为依据。
缓存要考虑失效，批量操作要考虑部分失败。短代码不等于快代码，少文件也不等于高效率。

测试关注外部可观察行为、边界、失败恢复和接口兼容性，不复刻实现步骤。
修改行为时运行相关测试；仅文档和注释修改无需新增重复行为测试。
提交前检查注释真实性、相关链接和配置示例，并明确哪些验证已做、哪些尚未完成。
项目专属硬件、部署、数据保护和外部副作用约束放在项目规范中具体说明。

## 参数说明补充要求（2026-11-03）

每个显式函数参数与配置参数都要有对应中文说明。此要求优先于简单函数可以仅写摘要的默认简写规则。Python用Args，C++用@param；YAML逐键说明。接收者self/cls及C++未命名形参例外按AI_REVIEW.md记录，不豁免单位、范围和语义真实性审查。
